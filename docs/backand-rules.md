# Правила архитектуры backend

Система бронирования залов вуза. Эти правила обязательны для всего нового кода.
Если задача требует их нарушить, сначала остановись и объясни почему, не нарушай молча.

## Стек

Python 3.14, FastAPI, SQLAlchemy 2.0 (async, asyncpg), Alembic, Pydantic v2, PostgreSQL 14+.
Новые библиотеки без запроса не добавлять. Поля и эндпоинты не выдумывать: источник правды
это модели и существующие схемы.

## Структура

```
app/
  core/          config, базовые исключения, dependencies (DbSession, CurrentUser, SuperUser),
                 mixins, security, pagination (PaginatedResponse)
  db/            postgres.py (engine, Base, get_db), models.py (импорт ВСЕХ моделей для Alembic)
  domains/
    <domain>/
      models.py
      schemas.py
      repository.py
      services.py
      exceptions.py
      dependencies.py
      router.py
  main.py
migrations/
tests/
```

Текущие домены: users, departments, buildings, rooms (+ moderators), event_formats, bookings.

## Направление зависимостей

```
router → dependencies → services → repository → models
              schemas используются в router, services, repository (только Filter)
```

1. `core` не импортирует `domains`. Никогда.
2. Слой выше может импортировать слой ниже, обратный импорт запрещён.
3. Между доменами зависимость идёт в одну сторону: `users ← rooms ← bookings`.
   Цикл между доменами означает ошибку проектирования: вынеси общее в `core` или
   в третий домен, а не импортируй друг в друга.
4. Чужой домен можно использовать так: `models` (внешние ключи, `relationship("Имя")` строкой),
   `exceptions`, `dependencies`, публичные методы `services`. Читать чужие таблицы через их
   репозиторий допустимо. Писать в чужие таблицы можно только через сервис владельца.
5. Роутер домена A подключается в `main.py`, а не внутрь роутера домена B, если A зависит от B.

## Что пишем в каждом слое

### models.py
Пишем: таблицы SQLAlchemy, колонки, enum, ограничения (`CheckConstraint`, `UniqueConstraint`,
`ExcludeConstraint`, `Index`), связи `relationship`.
Не пишем: бизнес-логику, запросы, импорт `schemas`/`services`/`repository`, `commit`.
- Правила целостности (уникальность, пересечения интервалов, диапазоны) живут в БД, а не только в коде.
- Связи только `lazy="raise"`, только «в одну сторону». Обратные списки (`Room.bookings`)
  не заводить, если список может быть большим.
- `Mapped[T]` обязателен всегда, `mapped_column(...)` только когда нужны настройки.
  Все `datetime` это `DateTime(timezone=True)` (через `type_annotation_map` в `Base`).
- Enum хранить значениями в нижнем регистре (`values_callable`), тип именовать.
- Значения по умолчанию дублировать через `server_default`.
- Внешние ключи: `ondelete` выбирать осознанно (`RESTRICT` для справочников и пользователей).
  Сущности, на которые ссылаются записи, не удаляем физически, а деактивируем (`is_active`).
- Индексы на внешние ключи PostgreSQL не создаёт сам, добавляй где нужны запросы.

### schemas.py
Пишем: Pydantic-модели `<Entity>Create`, `<Entity>Update`, `<Entity>Response`, `<Entity>Filter`;
проверки формата и внутренних инвариантов (`end_at > start_at`, длина, `gt=0`, `AwareDatetime`).
Не пишем: обращения к БД, правила, зависящие от данных («зал занят», «пользователь существует»),
`password_hash` и прочее секретное в `Response`.
- `Response` с `from_attributes=True`; обязательность полей совпадает с моделью (`nullable` ↔ `| None`);
  имена атрибутов совпадают с моделью.
- `Update` содержит только то, что можно менять. Права (`is_admin`), пароль, статус меняются
  отдельными методами и схемами.
- Пустые строки для необязательных полей нормализовать в `None` (`field_validator(mode="before")`).
- Вложенные объекты в `Response` допустимы только если репозиторий их загружает.

### repository.py
Пишем: весь SQL (`select`, `where`, `join`, `options`), методы `get_by_id`, `search`/`list` с
фильтрами и пагинацией, `find_*`, `create` (`add` + `flush`), `_load_options()`, общие условия
в `_conditions()` (одно правило в одном месте).
Не пишем: `commit`/`rollback`, бизнес-правила, проверку прав, `HTTPException`, доменные исключения,
сборку `Response`-схем.
- Возвращает ORM-объекты или списки (`list(...)`, не `Sequence`).
- Связи загружает явно: `joinedload` для «многие к одному», `selectinload` для коллекций.
  Лёгкие методы (для аутентификации) отдельно от «с подгрузкой».
- После `flush` не вызывает `refresh` ради связей (он их не загружает).
- Поиск по тексту только через `icontains(..., autoescape=True)`; ограничение `limit` обязательно.
- Один репозиторий отвечает за одну основную сущность.

### services.py
Пишем: бизнес-правила, оркестрацию нескольких репозиториев, проверку прав (`can_*`),
транзакцию (`commit`/`rollback`), перевод ошибок БД в доменные исключения, логирование,
возврат `Response`-схем (`model_validate`).
Не пишем: SQL напрямую, `Request`, `Depends`, `HTTPException`, `status`, любую связанность с HTTP.
- Порядок в операции записи: проверить права → проверить правила → понятная проверка до записи
  (например, `find_conflicts`) → запись → один `commit` → перечитать объект через `get_by_id`
  с нужными связями → вернуть схему.
- `IntegrityError` ловим в сервисе: `23505` уникальность, `23503` внешний ключ,
  `23P01` пересечение интервалов. Проверка до записи нужна ради сообщения, ограничение в БД
  остаётся окончательной защитой от гонок.
- Константы правил (шаг времени, лимиты) в `constants.py`, не магические числа.
- События, которые важны пользователям (создание, решение, смена прав), логируются;
  позже заменяются записью в `audit_log` в той же транзакции.

### exceptions.py
Пишем: доменные исключения, наследники базовых из `core.exceptions`
(`NotFoundError`, `ConflictError`, `BadRequestError`, `PermissionDeniedError`).
Не пишем: `HTTPException`, HTTP-коды (они заданы базовыми классами).
- Один класс на ситуацию, `detail` по умолчанию на русском. Свой текст передаётся аргументом:
  `raise BookingInvalid("Нельзя создать запись в прошлом")`.
- Тексты для пользователя: без имён таблиц, SQL и внутренних идентификаторов.
- Обработчик `AppError` один, глобальный, в `core`. В роутерах `try/except` для доменных ошибок не пишем.

### dependencies.py
Пишем: фабрики сервисов (`get_xxx_service`), проверки допуска по данным запроса
(`require_room_moderator`), `Annotated`-алиасы (`RoomManager`, `XxxServiceDep`).
Не пишем: бизнес-логику (зависимость вызывает метод сервиса), SQL.
- Общее для всех доменов (`DbSession`, `CurrentUser`, `SuperUser`) лежит в `core/dependencies.py`.
- Зависимость используется, когда нужные данные есть в адресе запроса (`room_id` в пути).
  Если объект известен только после чтения из БД, права проверяет сервис.

### router.py
Пишем: путь, метод, `response_model`, `status_code`, `summary`, `responses` с описанием ошибок,
параметры; один вызов метода сервиса; возврат результата.
Не пишем: логику, SQL, `commit`, создание сервиса внутри функции (только через `Depends`),
`try/except` доменных ошибок.
- Статические пути объявляются раньше параметрических (`/rooms/my` до `/rooms/{room_id}`).
- Фильтры списков: `Annotated[XxxFilter, Query()]`. Списки возвращают `PaginatedResponse[T]`;
  справочники без пагинации.

### db/models.py
Только импорты всех моделей (`# noqa: F401`). Импортируется в `main.py` и в `migrations/env.py`.

## Транзакции и сессия

- `async_sessionmaker(expire_on_commit=False)`.
- Репозиторий: `add` + `flush`. Сервис: один `commit` в конце операции, `rollback` при ошибке.
- Одна сессия на запрос (`get_db` через `Depends`, кэшируется внутри запроса).
- Несколько изменений одной операции (например, запись и `audit_log`) только в одной транзакции.

## Время

- В БД `timestamptz` (хранится в UTC). В API ISO 8601 с поясом, входящие поля `AwareDatetime`.
- В коде только `datetime.now(timezone.utc)`. Запрещены `datetime.now()` и `datetime.utcnow()`.
- Часы работы (`open_from`, `open_until`) это `Time` без пояса. Сравнивать только после перевода
  момента в пояс корпуса: `start_at.astimezone(ZoneInfo(building.timezone)).time()`.
- Границы «сегодня» и «завтра» считать в поясе корпуса, затем переводить в UTC для запроса.
- Интервалы полуоткрытые `[start, end)`. Пересечение: `a.start < b.end AND a.end > b.start`.
- Сессия PostgreSQL работает в `timezone=UTC`.

## Права

- Админ: `users.is_admin`. Модератор: назначение на зал (`room_moderators`, со сроком и отзывом).
  Единственная точка проверки: `can_moderate(user, room_id)`, админ проходит всегда.
- Права на сервере проверяются всегда, фронтенд лишь скрывает лишнее.
- Чужие объекты, существование которых нельзя раскрывать, отдают 404, а не 403.
- Передача прав: бессрочно назначает только админ, модератор передаёт на срок.

## API

- Префикс `/api/v1`, имена во множественном числе, смена статуса действием `POST /{id}/approve`.
- Коды: 201 создание, 204 без тела, 400 нарушено правило, 401, 403, 404, 409 конфликт
  (занято, недопустимый статус), 422 формат данных. Ошибка всегда `{"detail": "текст"}`.
- Фильтры списков имеют ограничения (`size` не больше 100, период календаря не больше 62 дней).

## Безопасность

- Пароли только хешем. `password_hash` не попадает ни в одну `Response`-схему и в логи.
- Секреты и токены в конфиге как `SecretStr`, в логи не пишутся.
- Токены экранов афиш хранятся хешем. `X-Forwarded-For` учитывается только от доверенных прокси.
- Обновление принимает только разрешённые поля, произвольный `dict` в `setattr` не отдавать.

## Стиль

- Типы везде. Синтаксис Python 3.12 (`str | None`, `list[int]`).
- Идентификаторы только латиницей (кириллическая «С» вместо «C» в имени класса ломает импорт
  и не видна глазами). Тексты ошибок, комментарии и docstring на русском.
- Имена: `<Entity>Repository`, `<Entity>Service`, `<Entity>Create/Update/Response/Filter`,
  `<Entity>NotFound`. Файлы в `snake_case`.
- Логгер: `logging.getLogger(__name__)`. Комментарий объясняет «почему», а не «что».
- Линтеры: ruff, mypy. Без неиспользуемых импортов.

## Миграции

- Любое изменение модели сопровождается миграцией Alembic. Автогенерацию читать глазами.
- Расширения (`btree_gist`) создаются в миграции до таблиц, которые их используют.
- `ExcludeConstraint` проверять вручную: автогенерация не всегда его создаёт.
- Данные не удаляются миграцией без явной просьбы.

## Тесты

- pytest, httpx `AsyncClient`, тестовая БД PostgreSQL (SQLite не подходит из-за `gist`).
- Подмена пользователя через `app.dependency_overrides`.
- Обязательные сценарии для записей: соседние интервалы не конфликтуют; пересечение даёт 409;
  две одновременные записи на один слот (`asyncio.gather`), проходит одна; запись вне часов работы
  отклоняется; обычный пользователь не может одобрить; закрытая запись в календаре «Занято».

## Как добавить домен

1. `models.py`, импорт в `db/models.py`, миграция.
2. `schemas.py`, `repository.py`, `exceptions.py`.
3. `services.py` с бизнес-правилами и транзакциями.
4. `dependencies.py`, `router.py`.
5. Подключение роутера в `main.py` с учётом порядка маршрутов.
6. Тесты на правила и права.

## Чеклист самопроверки перед ответом

- В `repository.py` нет `commit`, правил и исключений?
- В `services.py` нет `select`, `HTTPException`, `Depends`?
- В `router.py` один вызов сервиса и нет логики?
- Каждая связь, которую читает `Response`, загружена в репозитории?
- Все `datetime` с поясом, времена сравниваются в поясе корпуса?
- Ограничение целостности есть и в БД, и (для понятной ошибки) проверка в сервисе?
- Нет импорта, который ведёт «вверх» по слоям или создаёт цикл между доменами?
- Права проверяются на сервере, чужие объекты не раскрываются?

## Чего не делать

- Не складывать логику в роутеры и модели, SQL в сервисы, правила в схемы.
- Не коммитить в репозитории, не использовать `refresh` для загрузки связей.
- Не использовать ленивую загрузку, обратные списки «на всякий случай», `datetime.now()`.
- Не выдумывать поля и эндпоинты, не менять архитектуру без запроса.
